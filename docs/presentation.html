Motivation

The Problem with Traditional Layering

Classic approach — business logic leaks into every layer:
// Controller knows about persistence details
@GetMapping
public List<User> getAll() {
  return userRepository        // ← direct repo call
    .findByActiveTrue()       // ← MongoDB detail!
    .stream()
    .filter(User::isVerified) // ← biz logic in controller
    .toList();
}
  • ✗
    Hard to unit-test without a real database
  • ✗
    Swapping MongoDB → PostgreSQL touches every layer
  • ✗
    Business rules scattered across controllers & repos
Hexagonal approach — the core knows nothing about the outside:
// Service only knows about its port interface
@Service
public class UserService implements ListUsersUseCase {

  private final UserPersistencePort port; // interface!

  public UserPage getAll(...) {
    return port.findAll(...); // no MongoDB detail
  }
}
  • ✓
    Test business logic with zero infrastructure
  • ✓
    Swap DB by replacing one adapter class only
  • ✓
    Business rules in one predictable place
Architecture

Three Rings, One Rule

🔌 Adapters (outer ring) UserController · UserMongoPersistenceAdapter · DTOs
⬆ depends on ⬆
⚙️ Application (middle ring) UserService · Ports (interfaces) · Exceptions
⬆ depends on ⬆
💎 Domain (inner ring) User · UserPage — pure Java records
Dependencies point INWARD only Domain has ZERO framework imports Ports are just Java interfaces Spring wires implementations at runtime

💎 Domain model
record User(String id, String name, String address, Integer age)

Pure Java record. No annotations. No Spring. No MongoDB. The most stable thing in the codebase.
🔌 Ports = interfaces
Inbound ports describe what the app offers. Outbound ports describe what the app needs. Both live in the application layer.
🗺️ Mappers keep layers clean
Each boundary has its own mapper: UserRestMapper and UserMongoMapper translate without polluting domain objects.

// Controller — translate HTTP DTO → domain, call use case, translate back
@PostMapping @ResponseStatus(HttpStatus.CREATED)
public UserResponse create(@Valid @RequestBody CreateUserRequest req) {
  return mapper.toResponse(                   // 3. domain → HTTP DTO
           createUserUseCase.create(            // 2. call use case
             mapper.toDomain(req)));            // 1. HTTP DTO → domain
}

// Service — pure business logic, no HTTP/MongoDB knowledge
public User create(User user) {
  return persistencePort.save(
    new User(null, user.name(), user.address(), user.age())); // strip client id
}

Outbound Adapter

MongoDB Adapter — Dynamic Queries

@Override
public UserPage findAll(
    String name, Integer minAge,
    Integer maxAge, int page, int size) {

  // 1. Build optional filter criteria
  Query query = buildQuery(name, minAge, maxAge);

  // 2. Count BEFORE applying pagination
  long total = mongoTemplate.count(query, UserDocument.class);

  // 3. Apply pagination
  query.with(PageRequest.of(page, size));

  // 4. Fetch page, map documents → domain objects
  List<User> content = mongoTemplate
    .find(query, UserDocument.class)
    .stream().map(mapper::toDomain).toList();

  return new UserPage(content, total,
    (int) Math.ceil((double) total / size),
    page, size);
}

private Query buildQuery(String name, Integer min, Integer max) {
  Query q = new Query();
  if (name != null && !name.isBlank())
    q.addCriteria(Criteria.where("name").regex(name, "i"));
  if (min != null || max != null) {
    Criteria age = Criteria.where("age");
    if (min != null) age = age.gte(min);
    if (max != null) age = age.lte(max);
    q.addCriteria(age);
  }
  return q;
}
  • 1
    Optional filters — only criteria that are non-null are added to the query
  • 2
    Name filter uses a case-insensitive MongoDB regex /alice/i
  • 3
    Age range uses Mongo $gte / $lte — either bound is optional
  • 4
    Count before paginating so totalElements reflects all matches, not just one page
  • 5
    Domain objects returned — the service never sees a UserDocument

GET /api/users?name=ali&minAge=25&maxAge=35&page=0&size=10
Quality

Two-Layer Testing Strategy

🏎 Unit Tests — UserServiceTest
No Docker · No Spring · ~10ms
Tests all business logic in isolation using a Mockito mock of UserPersistencePort.

Covers: id-stripping on create · not-found exception · delegated pagination 
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

  @Mock UserPersistencePort persistencePort;

  @Test
  void createShouldStripClientId() {
    when(persistencePort.save(any())).thenReturn(saved);
    userService.create(new User("client-id", ...));
    verify(persistencePort).save(new User(null, ...)); // id = null
  }
}
🐳 Integration Tests — UserControllerIntegrationTest
Real MongoDB in Docker · Full Spring context
Testcontainers spins up a real mongo:7 container. @DynamicPropertySource injects the random port into Spring before context starts. 
@Testcontainers
class UserControllerIntegrationTest {

  @Container static MongoDBContainer mongo
    = new MongoDBContainer("mongo:7");

  @DynamicPropertySource
  static void mongoProps(DynamicPropertyRegistry r) {
    r.add("spring.data.mongodb.uri",
          mongo::getReplicaSetUrl);   // random port!
  }

  // Tests: create, get, update, delete,
  //        filter by name/age, pagination,
  //        validation errors (400)
}
Deployment

Docker Compose Stack

# docker-compose.yml
services:

  mongodb:
    image: mongo:7
    ports:
      - "27017:27017"
    volumes:
      - mongo_data:/data/db   # data persists

  app:
    build: .                  # multi-stage Dockerfile
    depends_on:
      - mongodb
    environment:
      MONGODB_URI: mongodb://mongodb:27017/hexagonal_demo
      SERVER_PORT: 8111
    ports:
      - "8111:8111"

volumes:
  mongo_data:
  • 1
    Multi-stage Dockerfile — Maven build stage + slim JRE runtime image, keeps image small
  • 2
    depends_on — Compose starts MongoDB before the app
  • 3
    Named volume — data survives container restarts
  • 4
    Environment variables — MONGODB_URI overrides application.yml at runtime

Takeaways

Why Hexagonal Architecture Pays Off

🔄
Replaceability
Swap MongoDB for PostgreSQL by writing one new adapter class. The domain and service layer don't change.
⚡
Fast Unit Tests
Business logic tested in milliseconds with zero Spring context, zero Docker, zero database. Just Java + Mockito.
🧩
Multiple Entry Points
Add a Kafka consumer or a CLI that reuses existing use cases — just write a new inbound adapter.
🎯
Single Responsibility
Every class has one job: translate (adapters) or orchestrate (service) or model (domain).
🔒
Domain Stability
User and UserPage are pure Java records. They never change due to a framework upgrade.
📖
Self-Documenting
Package names spell out the architecture. Any developer instantly knows where to add new code.
